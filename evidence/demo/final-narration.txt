ScopeLedger helps collections teams prepare invoice follow ups without handing an agent unlimited authority. This narrated walkthrough uses actual screens captured from our deployed demo and ArmorIQ account. Every customer and invoice is fictional. The product prepares three drafts and three tasks, while keeping payment references, recipients, account selection and data exports within explicit limits. The live application runs publicly on Texmed Google Cloud, so judges can inspect the same workflow themselves.

In live Gemini mode, Gemini 3.8 Flash on Vertex AI receives the real synthetic account notes and an injected payment redirection attachment. It proposes structured tool calls, and the executor checks each proposal. This captured run completed six of six approved actions with zero unauthorized effects. The model ignored the malicious note. We preserve its response identifier and token usage, and do not insert adversarial calls after model planning or claim this result proves model compromise.

The separate deterministic comparison deliberately attempts the forbidden payment change. Without controls, the isolated sandbox reference changes to the attacker demonstration value. With controls, the exact tool and argument check blocks that proposal, while all six legitimate actions still complete. The decision trail shows which operation was stopped and why. Draft recipients and payment references come from trusted account records, rather than text generated from an untrusted attachment. No email or payment is sent.

The evaluation lab measures usefulness as well as safety. Seven scenarios cover normal collections, payment redirection, recipient substitution, bulk export, scope escalation, duplicate actions and verifier outage. All seven passed. In the outage case, execution stops instead of treating a service failure as a successful policy denial. The source repository also runs nineteen tests, strict TypeScript, lint with zero warnings, a production build and a dependency audit in GitHub Actions. Engine coverage is measured separately.

We request a signed intent token and send the allowed workflow through the ArmorIQ proxy. It returns verified success and completes the synthetic workflow. We then use a separate signed plan containing the forbidden operation, ensuring the test reaches the proxy rather than stopping at the SDK original plan check. ArmorIQ policy blocks that operation.

The public application exposes the dated live verification report. It identifies the enforcement layer as ArmorIQ proxy policy and records the reason: the payment change tool is not allowed by policy. The report contains separate allowed and denied plan identifiers. Verification status is tied to the deployment revision that produced it. Local per action checks remain distinct from ArmorIQ cloud verification. Administrator credentials trigger new live proof runs, while judges can inspect the saved evidence without receiving credentials.

Our main takeaway is to measure the boundary at the point of action, while preserving useful work. A model ignoring an injection, a local executor rejecting arguments, and a cloud policy blocking a tool are different outcomes, and the evidence labels them separately. Next we would add authenticated tenant isolation, durable idempotency across runs, independently anchored audit hashes, and broader model evaluation.
